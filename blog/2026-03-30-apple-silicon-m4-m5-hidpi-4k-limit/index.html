Новый лимит HiDPI в Apple Silicon M4 и M5 на внешних 4K-дисплеях

30 марта 2026 · 15 мин чтения
Оригинал: Stephen McLeod

Начиная с M4 и включая новое поколение Apple Silicon M5, macOS больше не предлагает и не позволяет использовать полноразмерные HiDPI-режимы 4K для внешних дисплеев.

Максимальный доступный HiDPI-режим на панели 3840x2160 теперь — всего лишь 3360x1890 (с backing store 6720x3780 вместо 7680x4320). На машинах с M2/M3 этого ограничения не было.

Из-за этого регресса Apple фактически оставляет пользователю выбор между:

  • Полным экранным пространством в 4K (3840x2160), но с размытым текстом, потому что HiDPI отключён.

или

  • Уменьшенным рабочим пространством на уровне 3.3K (3360x1890), но с чётким текстом (HiDPI), заметно меньшей полезной площадью и интерфейсом macOS, который выглядит нелепо раздутым.

Это не аппаратное ограничение

DCP (Display Coprocessor) сообщает одинаковые возможности и на M2 Max, и на M5 Max для одного и того же дисплея. Железо M5 Max, согласно собственным спецификациям Apple, поддерживает 8K (7680x4320) при 60 Гц. Но бюджет framebuffer’а на уровне GPU-драйвера для каждого pipe (IOMFBMaxSrcPixels) искусственно ограничивает Pipe 0 шириной 6720 пикселей — это ровно ширина backing store для 3360x1890 HiDPI. При этом остальные три pipe получают полные 7680 пикселей, чего достаточно для 3840x2160 HiDPI.

Диагностика и что уже пробовали

Display Override Plist (scale-resolutions)

Что делалось: был создан display override plist в /Library/Displays/Contents/Resources/Overrides/DisplayVendorID-1e6d/DisplayProductID-7750 с записями scale-resolutions для 7680x4320 HiDPI.

Результат: на M5 Max это не дало эффекта. Тот же самый plist даёт 3840x2160 HiDPI на M2 Max. На M5 Max WindowServer отказывается вообще перечислять этот режим, независимо от содержимого plist.

Override plist, который работает на M2 Max:

<dict>
    <key>default-resolution</key>
    <data>AA8AAIhwAAAAPA==</data>  <!-- 3840x2160@60 -->
    <key>DisplayProductID</key>
    <integer>30544</integer>
    <key>DisplayVendorID</key>
    <integer>7789</integer>
    <key>scale-resolutions</key>
    <array>
        <data>AAAeAAAAEOAAAAAJACAAAA==</data>  <!-- 7680x4320 HiDPI -->
        <data>AAAeAAAAEOA=</data>               <!-- 7680x4320 -->
        <data>AAAPAAAACHA=</data>               <!-- 3840x2160 -->
    </array>
</dict>

Патчинг EDID (software override)

Что делалось: в ключ IODisplayEDID внутри override plist записывался пропатченный EDID со следующими изменениями:

  • Preferred timing удваивался до 4095x4095 (максимум 12-битного поля EDID)
  • Pixel clock выставлялся на максимум (655.35 MHz)
  • Пределы диапазона увеличивались до 2550 MHz max pixel clock, 255 kHz max H-freq, 255 Hz max V-freq

Результат: с такими значениями эффекта не было. Однако waydabber (разработчик BetterDisplay) подтвердил, что software EDID override может работать на M4: он получил 8K framebuffer на 4K TV, добавив корректный 8K timing и объявив его нативным разрешением. Вероятно, моя попытка не сработала потому, что 4095x4095 — это не реальный display timing. Но даже если override сделать правильно, 4K-панель физически не может принять 8K-сигнал. То есть это подтверждает механизм (scaled modes строятся из того, что система считает нативным разрешением), но не даёт практического решения.

Прошивка EDID в EEPROM монитора

Что делалось: был создан бинарный EDID с повышенными range limits (при этом preferred timing оставался нативным 3840x2160, чтобы не сломать вывод), затем предпринималась попытка прошить его в EEPROM монитора LG через функцию BetterDisplay “Upload EDID”.

Результат: прошивка не применилась. Монитор продолжил отдавать оригинальный EDID. Возможно, EEPROM у LG 32UN880 read-only, либо DDC-запись через BetterDisplay тихо провалилась. Даже если бы получилось, этот подход менял бы только range limits, но не preferred timing, из которого DCP берёт MaxW/MaxH.

Override через IOKit Registry (DisplayHints)

Что делалось: была попытка напрямую изменить словарь DisplayHints и массив ConnectionMapping у DCP в IOKit registry через IORegistryEntrySetCFProperty, подставив повышенные значения MaxW, MaxH и MaxActivePixelRate.

Результат: драйвер DCP явно отвергает запись свойств из userspace с kIOReturnUnsupported (kern_return=-536870201). Этими свойствами владеет kernel-level драйвер AppleDisplayCrossbar, и из userspace их изменить нельзя.

Повторное определение дисплея

Что делалось: использовался IOServiceRequestProbe, чтобы заставить DCP заново перечитать информацию о дисплее после записи override plist.

Результат: на список режимов это никак не повлияло. DCP перечитывает данные с физического дисплея, а не из software override.

Очистка кэша WindowServer

Что делалось: удалялись ~/Library/Preferences/ByHost/com.apple.windowserver.displays.*.plist, затем предпринималась попытка перезапустить WindowServer. Также выполнялась полная перезагрузка.

Результат: killall WindowServer в macOS 26 фактически не перезапускает WindowServer (нет ни мигания экрана, ни разрыва сессии). Полная перезагрузка с override plist на месте всё равно не дала режим 3840x2160 HiDPI. Дело не в кэше.

Уменьшение числа подключённых дисплеев

Что делалось: третий дисплей (U13ZA) отключался, чтобы проверить, не упирается ли всё в бюджет пропускной способности DCP между display pipe.

Результат: без изменений. Даже с двумя дисплеями (LG + встроенный) список режимов оставался тем же. Ограничение не связано с количеством подключённых дисплеев.

HDMI vs USB-C/Thunderbolt

Что делалось: рассматривался переход с USB-C/DisplayPort на HDMI.

Результат: не тестировалось; у HDMI 2.0 пропускная способность ниже (14.4 Gbps против 25.92 Gbps у DP 1.4 HBR3), так что результат был бы тем же или хуже.

Private API SkyLight (SLConfigureDisplayWithDisplayMode)

Что делалось: использовался SLConfigureDisplayWithDisplayMode из приватного фреймворка SkyLight, чтобы напрямую применить режим 3840x2160 HiDPI (7680x4320 pixel backing, scale=2.0) к дисплею LG. Режим брался как из списка CG modes, так и с других дисплеев.

Результат: возвращается error code 1000, если режима нет в собственном mode list дисплея. SkyLight API для конфигурации дисплеев валидирует режимы по тому же mode list, который строится из DCP, как и WindowServer. Приватного API-обхода этой валидации нет.

Где именно применяется лимит

DCP сообщает одинаковые capability-параметры на обеих машинах — MaxActivePixelRate, MaxW, MaxH, MaxTotalPixelRate совпадают. Это берётся из EDID дисплея, так что здесь всё ожидаемо.

Разница проявляется в mode list WindowServer. На M2 Max CGSGetNumberOfDisplayModes включает 3840x2160 при scale=2.0. На M5 Max, при тех же параметрах DCP и тех же override plist, такого режима просто нет.

IOMFBMaxSrcPixels — бюджет framebuffer на каждый pipe

IOMFBMaxSrcPixels на сервисе IOMobileFramebufferShim в IOKit раскрывает бюджеты размера framebuffer для каждого display pipe. На M5 Max, где LG сидит на Pipe 0:

"IOMFBMaxSrcPixels" = {
    "MaxSrcRectHeightForPipe" = (4608, 4608, 4608, 4608),
    "MaxSrcRectWidthForPipe"  = (6720, 7680, 7680, 7680),
    "MaxSrcBufferHeight"      = 16384,
    "MaxSrcBufferWidth"       = 16384,
    "IOMFBCompressionSupport" = 1
}

MaxSrcRectWidthForPipe — это массив с максимальной шириной backing store, которую GPU-драйвер готов выделить для каждого display pipe:

PipeMaxSrcRectWidthЧто это значит
06720Pipe монитора LG (подтверждено через ConnectionMapping PipeIDs)
17680Этого хватило бы для 3840x2160 HiDPI
27680Этого хватило бы для 3840x2160 HiDPI
37680Этого хватило бы для 3840x2160 HiDPI

Бюджет Pipe 0 в 6720 пикселей идеально совпадает с наблюдаемым потолком: для 3360x1890 HiDPI нужен backing store размером 6720x3780. Для 3840x2160 HiDPI нужен backing store шириной 7680 пикселей. У Pipe 0 на это не хватает бюджета, а у Pipe 1–3 хватает. То есть железо явно умеет это делать, просто LG оказался на «неудачном» pipe.

Это свойство задаётся kernel-level драйвером IOMobileFramebufferShim, и из userspace его изменить нельзя.

Бюджет фиксируется при загрузке

Тесты подтвердили, что MaxSrcRectWidthForPipe задаётся при загрузке драйвера и не меняется во время работы, что бы вы ни делали:

Возможно, драйвер читает содержимое EDID на ранней стадии boot и по нему решает, как распределять эти бюджеты (как предполагает анализ waydabber), но это пока не подтверждено cold boot-тестом с модифицированным EDID.

Что, вероятно, происходит

Разработчик BetterDisplay waydabber в discussion #4215 описывает изменение так:

“Generally 3840x2160 HiDPI is not available with any M4 generation Mac on non-8K displays due to the new dynamic nature of how the system allocates resources. There might be exceptions maybe - when the system concludes that no other displays could be attached and there are resources left still for a higher resolution framebuffer. But normally the system allocates as low framebuffer size as possible, anticipating further displays to be connected and saving room for those.”

Данные IOMFBMaxSrcPixels хорошо укладываются в это объяснение. M5 Max поддерживает до 4 внешних дисплеев, и GPU-драйвер при загрузке заранее распределяет framebuffer budgets между всеми pipe, исходя из максимальной конфигурации дисплеев, которую поддерживает чип. Pipe 0 получает уменьшенный бюджет 6720, чтобы оставить запас под дисплеи, которые ещё могут быть подключены. Даже в clamshell mode, когда подключён только LG, бюджет остаётся 6720 — драйверу неважно, сколько дисплеев реально подключено в данный момент.

Если собрать всё вместе:

  • DCP сообщает одинаковые capabilities на M2 Max и M5 Max (одинаковые MaxW, MaxH, MaxActivePixelRate)
  • На M5 Max MaxSrcRectWidthForPipe для Pipe 0 равен 6720, что ограничивает ширину backing store и, следовательно, потолок HiDPI на уровне 3360x1890
  • На M2 Max этого ограничения на pipe либо нет, либо на pipe для LG выделяется полноценные 7680
  • Отключение других дисплеев не меняет pipe budgets
  • Software EDID override действительно может влиять на генерацию режимов (waydabber подтвердил это, подменив нативное разрешение на 8K на M4), но только ценой лжи системе о нативном разрешении дисплея — а значит, сам дисплей не сможет использовать получившийся сигнал

Scaled resolution modes на M4/M5 строятся исходя из того, что система считает нативным разрешением дисплея. На M2/M3 система генерировала HiDPI-режимы вплоть до 2.0x от native resolution (то есть для 3840x2160 native получался backing store 7680x4320). На M4/M5 потолок теперь около 1.75x. Систему можно обмануть через EDID override, заставив её поверить в более высокое native resolution, но тогда дисплей не сможет принять такой сигнал. Для 4K-панелей это не практический workaround.

Что могло бы это исправить

Здесь нужен фикс со стороны Apple в механике распределения per-pipe budgets внутри драйвера IOMobileFramebufferShim. Конкретно: для Pipe 0 значение MaxSrcRectWidthForPipe должно быть 7680 вместо 6720, когда подключён дисплей 3840x2160. Несколько возможных вариантов:

  • Поднимать per-pipe budget до 7680, если нативное разрешение подключённого дисплея — 3840x2160
  • Перераспределять budgets по pipe исходя из реально подключённых дисплеев, а не держать резерв под worst-case scenario
  • Дать пользователю override для per-pipe framebuffer budgets (через системную настройку или nvram variable)

Проблема не в железе: на той же машине Pipe 1–3 уже имеют бюджеты шириной 7680. Автор отправил Apple Feedback FB22365722.

Для 5K- или 8K-панелей этот конкретный лимит может не проявляться так же жёстко, потому что их EDID native resolution уже достаточно высокое, и даже масштабирование на уровне 1.75x даёт приемлемый backing store.

Приложение: команды диагностики и вывод

Ниже — команды, с помощью которых можно воспроизвести наблюдения на любом Mac. Все, кроме №3, работают без специальных разрешений. Команда №6 — самая полезная для диагностики именно этой проблемы.

Диагностические команды

# 1. DCP rate limits and native caps per display
ioreg -l -w0 | grep -o '"MaxActivePixelRate"=[0-9]*\|"MaxW"=[0-9]*\|"MaxH"=[0-9]*' \
  | paste - - - | sort -u

# 2. System profiler display summary
system_profiler SPDisplaysDataType

# 3. All HiDPI modes for a display (requires Screen Recording permission)
#    Use BetterDisplay, SwitchResX, or any tool that calls
#    CGSGetNumberOfDisplayModes / CGSGetDisplayModeDescriptionOfLength.
#    Example output format shown below.

# 4. Display connection details and DisplayHints
ioreg -l -w0 | grep -B5 -A2 'MaxActivePixelRate' | grep -v EventLog

# 5. ConnectionMapping (per-pipe allocation)
ioreg -l -w0 | grep "ConnectionMapping"

# 6. Per-pipe framebuffer budgets (the key constraint on M4/M5)
ioreg -l -w0 | grep "IOMFBMaxSrcPixels"

У Pipe 0 (а это pipe дисплея LG) значение MaxSrcRectWidthForPipe равно 6720 — это ровно ширина backing store для 3360x1890 HiDPI. Значение 7680, которое нужно для 3840x2160 HiDPI, доступно на остальных трёх pipe, но не на Pipe 0.

Ключевое наблюдение

Возможности, которые сообщает DCP, у M2 Max и M5 Max для одного и того же дисплея идентичны. Разница — в per-pipe framebuffer budget (IOMFBMaxSrcPixels), который выставляет IOMobileFramebufferShim: на M5 Max Pipe 0 получает бюджет шириной 6720, и из-за этого потолок HiDPI обрезается на 3360x1890 ещё до того, как WindowServer вообще строит свой список режимов.
