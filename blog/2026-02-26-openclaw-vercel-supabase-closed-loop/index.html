Я построил AI-компанию на OpenClaw + Vercel + Supabase — через две недели они управляют ей сами

26 февраля 2026 · 10 мин чтения
Оригинал: Vox (@Voxyz_ai)

6 AI-агентов, 1 VPS, 1 база данных Supabase — от «агенты умеют разговаривать» до «агенты автономно управляют сайтом» у меня заняло две недели. В этой статье — что именно «не хватает между», как это закрыть, и архитектура, которую можно забрать себе и применить.

Стартовая точка: у вас уже есть OpenClaw. И что дальше?

Если вы в последнее время игрались с AI-агентами, высок шанс, что у вас уже поднят OpenClaw.

Он закрывает большую проблему: даёт Claude (или другой LLM) инструменты — браузинг, работу с файлами, выполнение команд, расписания. Можно назначать cron-задачи агентам: ежедневные посты, почасовые «интел-сканы», периодические исследовательские отчёты.

Я тоже начинал(а) с этого.

Мой проект называется VoxYZ Agent World — это 6 AI-агентов, которые автономно ведут сайт из «пиксельного офиса». Стек довольно простой:

  • OpenClaw (на VPS): «мозг» агентов — круглые столы (roundtable), cron, deep research
  • Next.js + Vercel: фронтенд сайта + API слой
  • Supabase: единый источник правды для состояния (proposals, missions, events, memories)

Шесть ролей, у каждой своя работа: Minion принимает решения, Sage анализирует стратегию, Scout собирает разведданные, Quill пишет контент, Xalt ведёт соцсети, Observer делает проверку качества.

Cron-задачи в OpenClaw заставляют их «приходить на работу» каждый день. Roundtable даёт им обсуждать, голосовать и приходить к консенсусу.

Но это всё ещё «умеют говорить», а не «умеют управлять».

Всё, что агенты производят — черновики твитов, аналитика, контент — остаётся на выходе OpenClaw. Ничто не превращает это в реальное действие, и ничто не говорит системе «готово» после выполнения.

Между «агенты умеют выдавать результат» и «агенты умеют делать end-to-end» отсутствует целый цикл: execute → feedback → re-trigger. Про него и статья.

Как выглядит “замкнутый цикл”

Давайте сначала определим, что такое closed loop, чтобы не построить «не то».

По-настоящему автономной системе нужен цикл:

1) Агент предлагает идею (Proposal)

2) Проверка авто-аппрува (Auto-Approve)

3) Создание миссии (Mission)

4) Выполнение шагов (Steps)

5) Обратная связь в базу (статусы, логи, артефакты)

6) Триггеры/реакции запускают следующий виток

Без этого вы получаете «агенты пишут», но не «агенты делают».

Центральная мысль: *истина должна жить в базе*

Если у вас есть Supabase (или любая БД), то вся система должна опираться на неё:

  • Proposals, missions, steps
  • лимиты и политики
  • события и журналы
  • очереди реакций

OpenClaw — это отличный «мозг + руки», но контрольный контур (approval/monitoring) и «память о том, что реально произошло» должны быть снаружи и быть проверяемыми.

Proposal → Mission → Step: минимальные сущности

В моём случае это выглядит так:

  • Proposal — предложение выполнить работу (пока pending)
  • Mission — одобренная работа (approved/running/succeeded/failed)
  • Step — конкретный исполняемый шаг (queued/running/succeeded/failed)

Важный момент: *агенты не должны «сами себе ставить галочку»*. Они должны писать артефакты + статусы в базу, а система должна считать «готово» только по реальному состоянию всех шагов.

Авто-аппрув и cap gates

Чтобы система могла работать без человека, нужны правила:

  • какие типы шагов можно пропускать без ручного подтверждения
  • дневные/часовые квоты
  • rate limits на внешние API

Эти правила я храню в ops_policy (JSON), чтобы можно было менять поведение без деплоя.

Исполнение: worker на VPS и контракт обновления статусов

Я использую worker, который берёт queued step, резервирует его, выполняет и возвращает результат:

  • обновляет status
  • пишет last_error при падении
  • кладёт артефакты (текст, ссылки, файлы)

После каждого шага обязательно вызывается maybeFinalizeMissionIfDone:

  • если любой step failed → mission failed
  • если все steps succeeded → mission succeeded

Нельзя отмечать mission как succeeded только потому что «один шаг прошёл». Это один из типичных багов.

Триггеры: обнаружить событие — не значит выполнить действие

Триггеры у меня только детектят, а не «трогают базу напрямую». Они формируют шаблон proposal и отправляют его в proposal service. Дальше всё проходит через cap gates и авто-аппрув.

Примерно так (логика/таблица в духе оригинала):

  • Новый твит (engagement > 5%) → Growth анализирует почему он завирусился (через 2 часа)
  • Mission failed → Sage диагностирует причину (через 1 час)
  • Новый контент опубликован → Observer проверяет качество (через 2 часа)
  • Insight собрал много апвоутов → авто-промоут в permanent memory (через 4 часа)

Cooldown важен. Без него один вирусный твит будет триггерить анализ на каждом heartbeat (например, каждые 5 минут).

Матрица реакций (reaction matrix)

Самая интересная часть — спонтанное взаимодействие агентов.

В таблице ops_policy хранится reaction_matrix:

{
  "patterns": [
    { "source": "twitter-alt", "tags": ["tweet","posted"], "target": "growth",
      "type": "analyze", "probability": 0.3, "cooldown": 120 },
    { "source": "*", "tags": ["mission:failed"], "target": "brain",
      "type": "diagnose", "probability": 1.0, "cooldown": 60 }
  ]
}

Xalt постит твит → с вероятностью 30% Growth анализирует его эффективность. Любая миссия падает → с вероятностью 100% Sage диагностирует.

probability — это не баг, а фича. 100% детерминизм = робот. Немного случайности = ощущение настоящей команды, где «иногда кто-то откликается, иногда нет».

Self-healing: системы будут застревать

Рестарты VPS, сетевые глюки, таймауты API — шаги могут зависнуть в статусе running, хотя по факту никто уже ничего не выполняет.

В heartbeat у меня есть recoverStaleSteps:

// 30 минут без прогресса → помечаем failed → проверяем, можно ли финализировать миссию
const STALE_THRESHOLD_MS = 30 * 60 * 1000;

const { data: stale } = await sb
  .from('ops_mission_steps')
  .select('id, mission_id')
  .eq('status', 'running')
  .lt('reserved_at', staleThreshold);

for (const step of stale) {
  await sb.from('ops_mission_steps').update({
    status: 'failed',
    last_error: 'Stale: no progress for 30 minutes',
  }).eq('id', step.id);
  await maybeFinalizeMissionIfDone(sb, step.mission_id);
}

maybeFinalizeMissionIfDone проверяет все steps в миссии: любой failed = миссия failed, все completed = success. Больше нет ситуации «один шаг прошёл — значит вся миссия success».

Полная архитектура

Три слоя с чёткими зонами ответственности:

  • OpenClaw (VPS): Think + Execute (brain + hands)
  • Vercel: Approve + Monitor (control plane)
  • Supabase: All state (shared cortex)

Что можно забрать себе

Если у вас OpenClaw + Vercel + Supabase, вот минимальный чеклист «замкнутого цикла»:

1) Таблицы в базе (Supabase)

Нужно минимум это:

| Таблица | Назначение |

|---|---|

| ops_mission_proposals | proposals (pending/accepted/rejected) |

| ops_missions | missions (approved/running/succeeded/failed) |

| ops_mission_steps | шаги выполнения (queued/running/succeeded/failed) |

| ops_agent_events | event stream (все действия агентов) |

| ops_policy | политики (auto_approve, x_daily_quota и т.п. как JSON) |

| ops_trigger_rules | правила триггеров |

| ops_agent_reactions | очередь реакций |

| ops_action_runs | execution logs |

2) Proposal service (один файл)

Сведите создание proposal + cap gates + auto-approve + создание mission в одну функцию. Все источники (API, triggers, reactions) должны вызывать её. Это хаб всего цикла.

3) Policy-driven конфигурация (таблица ops_policy)

Не хардкодьте лимиты. Все переключатели поведения должны жить в ops_policy.

// auto_approve: какие типы шагов можно пропускать автоматически
{ "enabled": true, "allowed_step_kinds": ["draft_tweet","crawl","analyze","write_content"] }

// x_daily_quota: дневной лимит твитов
{ "limit": 8 }

// worker_policy: исполняет ли Vercel шаги (false = только VPS)
{ "enabled": false }

Можно менять политики в любой момент без редеплоя.

4) Heartbeat (один API route + одна строка в crontab)

/api/ops/heartbeat на Vercel. Crontab на VPS, который дергает его каждые 5 минут. Внутри: оценка триггеров, обработка reaction queue, промоут инсайтов, очистка stale задач.

5) Контракт VPS worker

Каждый step kind должен маппиться на worker. После выполнения шага worker вызывает maybeFinalizeMissionIfDone, чтобы корректно финализировать миссию. Никогда не отмечайте mission как succeeded «потому что один шаг завершился».

Таймлайн на 2 недели

| Фаза | Время | Что было сделано |

|---|---:|---|

| Инфраструктура | было заранее | OpenClaw VPS + Vercel + Supabase |

| Proposals + Approval | 3 дня | Proposals API + auto-approve + policy table |

| Execution engine | 2 дня | mission-worker + 8 executors |

| Triggers + Reactions | 2 дня | 4 типа триггеров + reaction matrix |

| Loop unification | 1 день | proposal-service + cap gates + фиксы трёх типовых ловушек |

| Affect system + визуал | 2 дня | переработка affect + idle behavior + pixel office интеграция |

| Seed + Go Live | 0.5 дня | миграции + seed policies + crontab |

Если не считать уже существующую инфраструктуру, core closed loop (propose → execute → feedback → re-trigger) можно связать примерно за неделю.

Финальные мысли

Эти 6 агентов теперь каждый день автономно управляют voxyz.space. Я всё ещё оптимизирую систему ежедневно — подкручиваю политики, расширяю trigger rules, улучшаю сотрудничество агентов.

До идеала далеко: взаимодействие между агентами пока базовое, а «свобода воли» в основном симулируется вероятностной недетерминированностью. Но система реально работает и реально не требует, чтобы за ней постоянно следили.

В следующей статье я расскажу, как агенты «спорят» и «убеждают» друг друга — как голосование в roundtable и консолидация памяти Sage превращают 6 независимых инстансов Claude во что-то похожее на командное мышление.

Если вы строите агентные системы на OpenClaw — с радостью сравню заметки. Когда вы инди-разработчик и делаете такое, каждый разговор спасает от очередной типовой ямы.
