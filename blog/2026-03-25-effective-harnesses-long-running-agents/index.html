Эффективные harness'ы для долгоживущих агентов

25 марта 2026 · 15 мин чтения
Оригинал: Justin Young

Эффективные harness'ы для долгоживущих агентов

По мере того как ИИ-агенты становятся всё более способными, разработчики всё чаще поручают им сложные задачи, требующие работы на протяжении часов или даже дней. Однако обеспечение стабильного прогресса агентов при работе в нескольких context window'ах остаётся открытой проблемой.

Ключевая сложность долгоживущих агентов заключается в том, что они вынуждены работать дискретными сессиями, и каждая новая сессия начинается без какой-либо памяти о предыдущей. Представьте себе программный проект, над которым работают инженеры посменно, и каждый новый инженер приходит, ничего не зная о том, что происходило на предыдущей смене. Поскольку context window ограничен, а большинство сложных проектов невозможно завершить в рамках одного окна, агентам необходим способ преодолевать разрыв между сессиями.

Мы разработали двухкомпонентное решение, позволяющее Claude Agent SDK эффективно работать на протяжении множества context window'ов: initializer agent, который настраивает окружение при первом запуске, и coding agent, задача которого — обеспечивать инкрементальный прогресс в каждой сессии, оставляя понятные артефакты для следующей. Примеры кода можно найти в прилагаемом quickstart.

Проблема долгоживущих агентов

Claude Agent SDK — это мощный универсальный agent harness, хорошо справляющийся с написанием кода, а также с другими задачами, требующими от модели использования инструментов для сбора контекста, планирования и выполнения. Он обладает возможностями управления контекстом, такими как compaction, что позволяет агенту работать над задачей, не исчерпывая context window. Теоретически, при такой архитектуре агент должен быть способен выполнять полезную работу сколь угодно долго.

Однако одного compaction'а недостаточно. Из коробки даже передовая модель для написания кода, такая как Opus 4.5, работающая на Claude Agent SDK в цикле через несколько context window'ов, не сможет создать веб-приложение продакшн-качества, если ей дан лишь высокоуровневый промпт, например «создай клон claude.ai».

Неудачи Claude проявлялись в двух паттернах. Во-первых, агент стремился сделать слишком много за раз — по сути, пытался реализовать приложение целиком за один подход. Нередко это приводило к тому, что у модели заканчивался контекст посреди реализации, и следующая сессия начиналась с наполовину реализованной и недокументированной фичи. Агенту приходилось угадывать, что произошло, и тратить значительное время на то, чтобы вернуть приложение в рабочее состояние. Это происходит даже при compaction'е, который не всегда передаёт достаточно ясные инструкции следующему агенту.

Второй режим сбоя часто возникал на более поздних этапах проекта. После того как часть фич уже была реализована, очередной экземпляр агента осматривался, видел, что прогресс есть, и объявлял работу завершённой.

Это раскладывает проблему на две части. Во-первых, необходимо настроить начальное окружение, закладывающее фундамент для *всех* фич, которые требуются по заданному промпту, и направляющее агента на пошаговую работу — фича за фичей. Во-вторых, следует промптить каждого агента так, чтобы он обеспечивал инкрементальный прогресс к цели, при этом оставляя окружение в чистом состоянии по завершении сессии. Под «чистым состоянием» мы понимаем код, который было бы уместно влить в основную ветку: нет серьёзных багов, код упорядочен и хорошо документирован, и в целом разработчик может легко приступить к работе над новой фичей, не разбираясь сначала в чужом беспорядке.

В ходе внутренних экспериментов мы решали эти проблемы с помощью двухчастного подхода:

  1. Initializer agent: Самая первая сессия агента использует специализированный промпт, который просит модель настроить начальное окружение: скрипт init.sh, файл claude-progress.txt, ведущий лог действий агентов, и первоначальный git-коммит, показывающий, какие файлы были добавлены.
  2. Coding agent: Каждая последующая сессия просит модель обеспечить инкрементальный прогресс, а затем оставить структурированные обновления.[^1]

Ключевой инсайт состоял в том, чтобы найти способ для агентов быстро понимать состояние работы при старте с чистым context window'ом — это достигается с помощью файла claude-progress.txt совместно с git-историей. Вдохновением для этих практик послужило знание того, что эффективные инженеры-разработчики делают каждый день.

Управление окружением

В обновлённом руководстве по промптингу Claude 4 мы поделились лучшими практиками для рабочих процессов с несколькими context window'ами, включая структуру harness'а, использующую «отдельный промпт для самого первого context window'а». Этот «отдельный промпт» просит initializer agent настроить окружение со всем необходимым контекстом, который понадобится будущим coding agent'ам для эффективной работы. Здесь мы подробнее рассмотрим некоторые ключевые компоненты такого окружения.

Feature list

Чтобы решить проблему попытки агента реализовать приложение за один подход или преждевременного объявления проекта завершённым, мы промптили initializer agent составить исчерпывающий файл с требованиями к фичам, расширяющий исходный промпт пользователя. В примере с клоном claude.ai это означало более 200 фич, таких как «пользователь может открыть новый чат, ввести запрос, нажать Enter и увидеть ответ ИИ». Все эти фичи изначально отмечались как «не пройденные» (failing), чтобы последующие coding agent'ы имели чёткое представление о полной функциональности.

{
    "category": "functional",
    "description": "New chat button creates a fresh conversation",
    "steps": [
      "Navigate to main interface",
      "Click the 'New Chat' button",
      "Verify a new conversation is created",
      "Check that chat area shows welcome state",
      "Verify conversation appears in sidebar"
    ],
    "passes": false
  }

Мы промптим coding agent'ов редактировать этот файл, только изменяя статус поля passes, и используем строгие формулировки, такие как «Недопустимо удалять или редактировать тесты, так как это может привести к потере или некорректной работе функциональности». После ряда экспериментов мы остановились на JSON-формате, поскольку модель реже некорректно изменяет или перезаписывает JSON-файлы по сравнению с Markdown-файлами.

Инкрементальный прогресс

При наличии такого начального окружения следующая итерация coding agent'а получала задание работать только над одной фичей за раз. Этот инкрементальный подход оказался критически важным для решения проблемы стремления агента сделать слишком много за один раз.

При инкрементальной работе по-прежнему важно, чтобы модель оставляла окружение в чистом состоянии после внесения изменений в код. В наших экспериментах мы обнаружили, что лучший способ добиться такого поведения — попросить модель коммитить свой прогресс в git с описательными сообщениями коммитов и записывать сводки своего прогресса в progress file. Это позволяло модели использовать git для отката плохих изменений и восстановления рабочих состояний кодовой базы.

Эти подходы также повысили эффективность, поскольку устранили необходимость для агента гадать, что произошло, и тратить время на возвращение приложения в рабочее состояние.

Тестирование

Ещё один серьёзный режим сбоя, который мы наблюдали, — склонность Claude отмечать фичу как завершённую без надлежащего тестирования. Без явного промптинга Claude, как правило, вносил изменения в код и даже проводил тестирование с помощью юнит-тестов или команд curl к dev-серверу, но не замечал, что фича не работает end-to-end.

В случае создания веб-приложения Claude в основном хорошо справлялся с end-to-end-проверкой фич, когда ему явно предлагалось использовать инструменты браузерной автоматизации и проводить всё тестирование так, как это сделал бы живой пользователь.

*Скриншоты, сделанные Claude через Puppeteer MCP-сервер при тестировании клона claude.ai.*

Предоставление Claude подобных инструментов тестирования кардинально улучшило результаты, поскольку агент мог выявлять и исправлять баги, которые не были очевидны из одного лишь кода.

Некоторые проблемы остаются: ограничения зрения Claude и инструментов браузерной автоматизации затрудняют выявление всех типов багов. Например, Claude не может видеть нативные модальные окна браузера (alert) через Puppeteer MCP, и фичи, зависящие от таких модальных окон, в итоге содержали больше багов.

Вхождение в курс дела

С учётом всего вышесказанного, каждый coding agent получает промпт на выполнение ряда шагов для ориентации — некоторые из них довольно базовые, но всё равно полезные:

  1. *Выполните pwd, чтобы увидеть рабочую директорию. Вы сможете редактировать файлы только в этой директории.*
  2. *Прочитайте git-логи и progress file, чтобы понять, над чем работали в последнее время.*
  3. *Прочитайте файл feature list и выберите фичу с наивысшим приоритетом, которая ещё не реализована.*

Этот подход экономит Claude токены в каждой сессии, поскольку ему не нужно самостоятельно выяснять, как тестировать код. Также полезно попросить initializer agent написать скрипт init.sh, способный запускать dev-сервер, а затем провести базовый end-to-end-тест перед реализацией новой фичи.

В случае с клоном claude.ai это означало, что агент всегда запускал локальный dev-сервер и через Puppeteer MCP открывал новый чат, отправлял сообщение и получал ответ. Это гарантировало, что Claude мог быстро определить, было ли приложение оставлено в неработоспособном состоянии, и немедленно исправить существующие баги. Если бы агент вместо этого сразу приступил к реализации новой фичи, он, скорее всего, усугубил бы проблему.

С учётом всего этого типичная сессия начинается со следующих сообщений ассистента:

[Assistant] I'll start by getting my bearings and understanding the current state of the project.
[Tool Use] <bash - pwd>
[Tool Use] <read - claude-progress.txt>
[Tool Use] <read - feature_list.json>
[Assistant] Let me check the git log to see recent work.
[Tool Use] <bash - git log --oneline -20>
[Assistant] Now let me check if there's an init.sh script to restart the servers.
<Starts the development server>
[Assistant] Excellent! Now let me navigate to the application and verify that some fundamental features are still working.
<Tests basic functionality>
[Assistant] Based on my verification testing, I can see that the fundamental functionality is working well. The core chat features, theme switching, conversation loading, and error handling are all functioning correctly. Now let me review the tests.json file more comprehensively to understand what needs to be implemented next.
<Starts work on a new feature>

Дальнейшая работа

Данное исследование демонстрирует один из возможных наборов решений в harness'е долгоживущего агента, обеспечивающих инкрементальный прогресс модели на протяжении множества context window'ов. Тем не менее остаются открытые вопросы.

В частности, пока неясно, обеспечивает ли единый универсальный coding agent наилучшие результаты во всех контекстах, или лучшей производительности можно достичь с помощью мультиагентной архитектуры. Представляется разумным, что специализированные агенты — например, агент тестирования, агент контроля качества или агент очистки кода — могли бы ещё лучше справляться с подзадачами на различных этапах жизненного цикла разработки ПО.

Кроме того, данное демо оптимизировано для full-stack-разработки веб-приложений. Перспективным направлением является обобщение этих находок на другие области. Вероятно, часть или все эти уроки применимы к типам долгоживущих агентных задач, возникающих, например, в научных исследованиях или финансовом моделировании.
