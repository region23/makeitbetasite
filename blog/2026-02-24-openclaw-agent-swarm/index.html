OpenClaw + Codex/Claude Code: команда разработчиков из одного человека

24 февраля 2026 · 10 мин чтения
Оригинал: Elvis (@elvissun)

Я больше не использую Codex и Claude Code напрямую.

Я использую OpenClaw как оркестрационный слой. Мой оркестратор, Зои, спаунит агентов, пишет им промпты, выбирает нужную модель для каждой задачи, следит за прогрессом и пишет мне в Telegram, когда PR'ы готовы к мержу.

Результаты за последние 4 недели:

  • 94 коммита за один день — самый продуктивный день, при том что у меня было 3 клиентских звонка и я ни разу не открыл редактор. В среднем около 50 коммитов в день.
  • 7 PR'ов за 30 минут — от идеи до продакшна молниеносно, потому что код и валидация в основном автоматизированы.
  • Коммиты → MRR — я использую это для реального B2B SaaS, который строю: бандлю с founder-led продажами и доставляю большинство фичереквестов в тот же день. Скорость конвертирует лиды в платящих клиентов.

Мой git-history выглядит так, будто я только что нанял команду разработчиков. На самом деле это просто я: перешёл от управления Claude Code к управлению OpenClaw-агентом, который управляет флотом других агентов — Claude Code и Codex.

Успешность: система решает почти все маленькие и средние задачи с первого раза без вмешательства.

Стоимость: ~$100/месяц за Claude и $90/месяц за Codex, но начать можно с $20.

Вот почему это работает лучше, чем использовать Codex или Claude Code напрямую:

Codex и Claude Code знают очень мало о вашем бизнесе. Они видят код. Они не видят полной картины.

OpenClaw меняет уравнение. Он выступает оркестрационным слоем между вами и всеми агентами — хранит весь мой бизнес-контекст (данные клиентов, заметки с встреч, прошлые решения, что сработало, что провалилось) в Obsidian-хранилище и переводит исторический контекст в точные промпты для каждого coding-агента. Агенты остаются сосредоточены на коде. Оркестратор работает на уровне высокой стратегии.

Вот как система работает на высоком уровне:

На прошлой неделе Stripe написали о своей системе фоновых агентов под названием «Minions» — параллельные coding-агенты на основе централизованного оркестрационного слоя. Я случайно построил то же самое, но оно работает локально на моём Mac mini.

Прежде чем рассказать, как это настроить, — объясню, почему вам вообще нужен оркестратор.

Почему один ИИ не может делать всё

Контекстное окно — игра с нулевой суммой. Нужно выбирать, что туда попадает.

Заполните кодом — не останется места для бизнес-контекста. Заполните историей клиентов — не останется места для кодовой базы. Именно поэтому двухуровневая система работает: каждый ИИ загружен ровно тем, что ему нужно.

У OpenClaw и Codex кардинально разный контекст:

Специализация через контекст, а не через разные модели.

Полный воркфлоу из 8 шагов

Разберём реальный пример с прошлой недели.

Шаг 1: Запрос клиента → скоупинг с Зои

У меня был звонок с клиентом из агентства. Они хотели переиспользовать конфигурации, уже настроенные для команды.

После звонка я обсудил запрос с Зои. Поскольку все мои заметки с встреч автоматически синхронизируются в Obsidian-хранилище — никаких объяснений с моей стороны не потребовалось. Мы вместе проработали фичу и пришли к системе шаблонов, которая позволяет сохранять и редактировать существующие конфигурации.

Затем Зои делает три вещи:

  1. Пополняет кредиты, чтобы сразу разблокировать клиента — у неё есть admin API access.
  2. Достаёт конфиг клиента из prod-базы — у неё read-only доступ к prod DB (у моих Codex-агентов этого никогда не будет), чтобы получить текущую конфигурацию, которая включается в промпт.
  3. Спаунит Codex-агента — с детальным промптом, содержащим весь контекст.

Шаг 2: Запуск агента

Каждый агент получает свой worktree (изолированную ветку) и tmux-сессию:

# Создаём worktree + запускаем агента
git worktree add ../feat-custom-templates -b feat/custom-templates origin/main
cd ../feat-custom-templates && pnpm install

tmux new-session -d -s "codex-templates" \
  -c "/Users/elvis/Documents/GitHub/medialyst-worktrees/feat-custom-templates" \
  "$HOME/.codex-agent/run-agent.sh templates gpt-5.3-codex high"

Агент работает в tmux-сессии с полным терминальным логгингом через скрипт.

Вот как мы запускаем агентов:

# Codex
codex --model gpt-5.3-codex \
  -c "model_reasoning_effort=high" \
  --dangerously-bypass-approvals-and-sandbox \
  "Your prompt here"

# Claude Code
claude --model claude-opus-4.5 \
  --dangerously-skip-permissions \
  -p "Your prompt here"

Раньше я использовал codex exec или claude -p, но недавно перешёл на tmux.

tmux значительно лучше, потому что перенаправление по ходу задачи — это мощный инструмент. Агент идёт не туда? Не убивайте его:

# Неправильный подход — просто остановить:
tmux send-keys -t codex-templates "Stop. Focus on the API layer first, not the UI." Enter

# Нужно больше контекста:
tmux send-keys -t codex-templates "The schema is in src/types/template.ts. Use that." Enter

Задача отслеживается в .clawdbot/active-tasks.json:

{
  "id": "feat-custom-templates",
  "tmuxSession": "codex-templates",
  "agent": "codex",
  "description": "Custom email templates for agency customer",
  "repo": "medialyst",
  "worktree": "feat-custom-templates",
  "branch": "feat/custom-templates",
  "startedAt": 1740268800000,
  "status": "running",
  "notifyOnComplete": true
}

По завершению обновляется с номером PR и статусами проверок:

{
  "status": "done",
  "pr": 341,
  "completedAt": 1740275400000,
  "checks": {
    "prCreated": true,
    "ciPassed": true,
    "claudeReviewPassed": true,
    "geminiReviewPassed": true
  },
  "note": "All checks passed. Ready to merge."
}

Шаг 3: Мониторинг в цикле

Cron-задача запускается каждые 10 минут и следит за всеми агентами. По сути, это улучшенный Ralph Loop — подробнее чуть позже.

Но она не опрашивает агентов напрямую — это было бы дорого. Вместо этого она запускает скрипт, который читает JSON-реестр и проверяет:

.clawdbot/check-agents.sh

Скрипт на 100% детерминирован и крайне эффективен по токенам:

  • Проверяет, живы ли tmux-сессии
  • Проверяет открытые PR'ы на отслеживаемых ветках
  • Проверяет статус CI через gh cli
  • Автоматически перезапускает упавших агентов (максимум 3 попытки), если CI не прошёл или ревью дало критические замечания
  • Оповещает только если нужно человеческое вмешательство

Я не слежу за терминалами. Система сама говорит мне, когда смотреть.

Шаг 4: Агент создаёт PR

Агент коммитит, пушит и открывает PR через gh pr create --fill. В этот момент я уведомления не получаю — PR сам по себе ещё не значит «готово».

Определение готовности (очень важно, чтобы агент это знал):

  • PR создан
  • Ветка синхронизирована с main (нет конфликтов)
  • CI проходит (lint, types, unit tests, E2E)
  • Ревью Codex прошло
  • Ревью Claude Code прошло
  • Ревью Gemini прошло
  • Скриншоты прикреплены (если изменялся UI)

Шаг 5: Автоматическое код-ревью

Каждый PR рецензируется тремя AI-моделями. Они ловят разное:

  • Codex Reviewer — исключителен по части edge cases. Делает самое тщательное ревью. Ловит логические ошибки, отсутствующую обработку ошибок, race conditions. Процент ложных срабатываний очень низкий.
  • Gemini Code Assist Reviewer — бесплатный и невероятно полезный. Ловит проблемы безопасности, проблемы масштабируемости, которые другие агенты пропускают. И предлагает конкретные исправления. Обязателен к установке.
  • Claude Code Reviewer — в основном бесполезен: склонен к излишней осторожности. Много «рассмотрите добавление...» предложений, которые обычно являются оверинжинирингом. Я игнорирую всё, кроме пометок critical. Критических проблем он сам редко находит, но подтверждает то, что отмечают другие ревьюеры.

Все трое постят комментарии напрямую в PR.

Шаг 6: Автоматическое тестирование

Наш CI-пайплайн прогоняет большой объём автотестов:

  • Lint и TypeScript-проверки
  • Unit-тесты
  • E2E-тесты
  • Playwright-тесты против preview-окружения (идентичного prod)

На прошлой неделе я добавил новое правило: если PR меняет UI — в описании PR должен быть скриншот. Иначе CI падает. Это резко сокращает время ревью — я вижу ровно что изменилось, не кликая по preview.

Шаг 7: Ревью человека

Теперь я получаю уведомление в Telegram: «PR #341 готов к ревью».

К этому моменту:

  • CI прошёл
  • Три AI-ревьюера одобрили код
  • Скриншоты показывают изменения UI
  • Все edge cases задокументированы в комментариях ревью

Моё ревью занимает 5–10 минут. Многие PR'ы я мержу, не читая код — скриншот показывает мне всё необходимое.

Шаг 8: Мерж

PR мержится. Ежедневная cron-задача чистит осиротевшие worktrees и task registry JSON.

Ralph Loop V2

По сути, это Ralph Loop, но лучше.

Ralph Loop: достаёт контекст из памяти → генерирует вывод → оценивает результаты → сохраняет обучение. Но большинство реализаций гоняют один и тот же промпт в каждом цикле. Дистиллированные знания улучшают будущие ретривалы, но сам промпт остаётся статичным.

Наша система иная. Когда агент падает, Зои не просто перезапускает его с тем же промптом. Она смотрит на ошибку с полным бизнес-контекстом и разбирается, как разблокировать:

  • Агент исчерпал контекст? «Сосредоточься только на этих трёх файлах.»
  • Агент пошёл не туда? «Стоп. Клиент хотел X, не Y. Вот что он сказал на встрече.»
  • Агенту нужно уточнение? «Вот письмо клиента и чем занимается его компания.»

Зои сопровождает агентов до завершения. У неё есть контекст, которого нет у агентов — история клиентов, заметки с встреч, что пробовали раньше, почему не сработало. Она использует этот контекст, чтобы писать лучшие промпты при каждой повторной попытке.

Но она также не ждёт, пока я назначу задачи. Она сама находит работу проактивно:

  • Утром: сканирует Sentry → находит 4 новые ошибки → спаунит 4 агента для расследования и исправления
  • После встреч: сканирует заметки → помечает 3 фичереквеста от клиентов → спаунит 3 Codex-агента
  • Вечером: сканирует git log → спаунит Claude Code для обновления changelog и документации для клиентов

Я иду на прогулку после клиентского звонка. Возвращаюсь в Telegram: «7 PR'ов готовы к ревью. 3 фичи, 4 багфикса.»

Когда агенты успешно справляются — паттерн логируется. «Эта структура промпта работает для billing-фич.» «Codex нужны type-определения заранее.» «Всегда включай пути к тест-файлам.»

Сигналы успеха: CI прошёл, все три код-ревью одобрили, человек смержил. Любой сбой запускает цикл. Со временем Зои пишет лучшие промпты — потому что помнит, что уехало в прод.

Выбор правильного агента

Не все coding-агенты одинаковы. Краткий справочник:

Codex — мой рабочий конь. Бэкенд-логика, сложные баги, мультифайловые рефакторинги — всё, что требует рассуждений по всей кодовой базе. Медленнее, но тщательнее. Использую для 90% задач.

Claude Code — быстрее и лучше во фронтенд-работе. Меньше проблем с разрешениями, поэтому отлично подходит для git-операций. (Раньше использовал его больше для повседневной работы, но Codex 5.3 теперь просто лучше и быстрее.)

Gemini — другая суперсила: дизайнерское чутьё. Для красивых UI я сначала прошу Gemini сгенерировать HTML/CSS-спецификацию, а потом передаю это Claude Code для реализации в нашей компонентной системе. Gemini проектирует — Claude строит.

Зои выбирает правильного агента для каждой задачи и маршрутизирует вывод между ними. Баг в billing-системе идёт к Codex. Исправление стиля кнопки — к Claude Code. Новый дизайн дашборда начинается с Gemini.

Как настроить

Скопируйте всю эту статью в OpenClaw и скажите ему: «Реализуй этот setup агентного роя для моей кодовой базы».

Он прочитает архитектуру, создаст скрипты, настроит структуру директорий и сконфигурирует cron-мониторинг. Готово за 10 минут.

Никаких курсов я вам не продаю.

Узкое горлышко, которого никто не ждёт

Вот в чём я упираюсь сейчас: оперативная память.

Каждому агенту нужен свой worktree. Каждому worktree нужны свои node_modules. Каждый агент запускает сборки, type-проверки, тесты. Пять агентов одновременно — это пять параллельных TypeScript-компиляторов, пять test-runner'ов, пять наборов зависимостей в памяти.

Мой Mac Mini с 16 ГБ упирается в потолок на 4–5 агентах, не начав свопиться — и нужно чтобы они не пытались собираться одновременно.

Поэтому я купил Mac Studio M4 Max с 128 ГБ RAM ($3 500) для этой системы. Приедет в конце марта — расскажу, стоило ли оно того.

Дальше: компания одного человека на миллион

В 2026 году мы увидим огромное количество компаний одного человека с миллионным оборотом. Рычаг колоссальный для тех, кто умеет строить рекурсивно самосовершенствующихся агентов.

Вот как это выглядит: AI-оркестратор как расширение вас самих (как Зои для меня), делегирующий работу специализированным агентам, которые отвечают за разные бизнес-функции. Разработка. Поддержка клиентов. Операции. Маркетинг. Каждый агент сосредоточен на том, в чём хорош. Вы сохраняете лазерный фокус и полный контроль.

Следующее поколение предпринимателей не будет нанимать команду из 10 человек, чтобы делать то, что один человек с правильной системой делает сам. Они будут строить так — оставаясь маленькими, двигаясь быстро, шипая каждый день.

Сейчас вокруг куча AI-слопа. Куча хайпа вокруг агентов и «mission control'ов» без реального строительства чего-то полезного. Красивые демо без real-world пользы.

Я стараюсь делать наоборот: меньше хайпа, больше документирования строительства настоящего бизнеса. Реальные клиенты, реальная выручка, реальные коммиты в продакшн и реальные потери тоже.

Что я строю? Agentic PR — компания одного человека, которая конкурирует с enterprise PR-гигантами. Агенты, которые помогают стартапам получать пресс-покрытие без ретейнера $10k/месяц.
