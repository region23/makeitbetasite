On-prem инфраструктура для AI-кодинга: как рассчитать серверы под GLM-5.1 и не разориться на 128K-контексте

19 апреля 2026 · 20 мин чтения

Вопрос «купить H100 или платить за Claude/Codex» окончательно устарел. Для российской компании в 2026 году правильный вопрос звучит иначе: можем ли мы построить on-prem coding-инфраструктуру на GLM-5.1 так, чтобы разработчики реально работали с длинным контекстом, а не стояли в очереди к GPU?

В этой статье мы не рассматриваем абстрактный чат на 4–8K токенов. Мы считаем реальный agentic coding-сценарий (Cline, Roo Code, Kilo Code или внутренние аналоги), который читает файлы, вызывает инструменты, смотрит diff-ы, запускает тесты и постоянно держит огромный контекст.

Целевая модель — GLM-5.1. Это флагманская MoE-модель Z.AI для сложных инженерных задач: 200K context, tool use, coding agents и выдающиеся результаты на SWE-Bench Pro / NL2Repo. В конфигурации модели указаны 78 слоев, 256 routed experts, 8 experts per token, kv_lora_rank=512, qk_rope_head_dim=64 и max_position_embeddings=202752. Эти параметры критичны не только для качества, но и для расчета пропускной способности.

Главное допущение: 1 активный разработчик = 128K контекста

Для сценария coding-agent нельзя считать пользователей по метрикам простых чатов. В разработке контекст забивается моментально: system prompt, описания инструментов, история действий, файлы, выводы тестов и фрагменты документации.

Поэтому закладываем жесткий стандарт:

1 активный разработчик = 128K input/context + 16K reserve на генерацию = 144K hot tokens.

Речь идет не о размере штата, а о количестве людей, которые *прямо сейчас* ждут ответа от модели. И здесь возникает главный bottleneck: формат NVFP4 радикально сжимает веса модели, но не отменяет стоимость KV-кэша.

Raw KV-cache для одной 144K-сессии GLM-5.1 рассчитывается по формуле:

$$144000 \times 78 \times (512 + 64) \times \text{bytes\_per\_element}$$

  • BF16 KV-cache: $\approx$ 12.9 GB на одну активную сессию.
  • FP8 KV-cache: $\approx$ 6.5 GB (при поддержке бэкендом).

На практике к этому добавляется запас на runtime buffers, фрагментацию аллокатора, CUDA graphs и overhead планировщика.

Ключевой вывод: сервер может вместить веса GLM-5.1, но все равно захлебнется от множества одновременных 128K-сессий.

Два пути: FP8 против NVFP4

Для запуска GLM-5.1 существуют два принципиальных подхода.

1. Путь FP8 (H200/B200-class)

Естественный выбор для H200. Фреймворк vLLM демонстрирует запуск GLM-5.1-FP8 на 8×H200 141GB (tensor parallel 8). Бенчмарки показывают пиковый throughput около 800 tokens/s, но mean Time To First Token (TTFT) уходит за 13 секунд даже на коротких запросах. Это надежный ориентир, но он не отражает нагрузку 128K.

2. Путь NVFP4 (Blackwell)

Этот 4-битный floating-point формат с microscaling реализован в Blackwell Tensor Cores (RTX PRO 6000 Blackwell, B200, GB200) и принципиально меняет экономику.

Веса NVFP4 занимают порядка 434–440 GB, что делает 8×RTX PRO 6000 Blackwell (96GB) минимально практичным конфигом. Однако из-за необходимости использовать BF16 для стабильного long-context serving, практическая емкость составляет всего около 314K токенов. Это буквально 1–2 активные 128K-сессии, несмотря на высокие показатели decode throughput на коротких промптах.

Экономика железа: реалии РФ на 2026 год

Российские реалии диктуют свои правила: санкционная логистика, НДС, отсутствие официальной гарантии — все это искажает цены. Расчет TCO ниже базируется на горизонте 6 лет (электричество 8 ₽/кВт⋅ч, поддержка/ЗИП 25% от CAPEX, 1 FTE поддержки $\approx$ 5 млн ₽/год). Курс: 76.05 ₽/$.

API vs. On-Premises: сравниваем с Claude/Codex

Доступ к API из РФ — это всегда компромисс между комплаенсом, рисками блокировок (о которых OpenAI прямо предупреждает) и сложными схемами оплаты. Но в качестве финансового бенчмарка этот вариант необходим.

При $100–200/мес. за пользователя (Claude Team/Pro) и активном использовании API:

  • Команда 20 человек: $\approx$ 14–27 млн ₽ за 6 лет.
  • Команда 200 человек: $\approx$ 140–270 млн ₽ за 6 лет (при росте нагрузки сумма легко уходит за 500 млн ₽).

Вывод: Для команды из 20 человек железо (от 70 млн ₽) не окупается напрямую деньгами. Это инвестиция в безопасность, интеграцию с внутренними контурами и отсутствие санкционных рисков. Для 200 человек on-prem становится экономически целесообразным.

Архитектура под размер команды

Сценарий: 20 разработчиков

Один сервер 8×RTX PRO 6000 — это лишь пилот. Для комфортной работы без жестких очередей минимально разумные варианты:

  • 2 узла 8×RTX PRO 6000 Blackwell (2–4 сессии одновременно).
  • 1 узел 8×B200 (6–8 сессий одновременно).

Требуется аккуратная эксплуатация: дефолтный контекст 32K/64K, а 128K выдается только по необходимости.

Сценарий: 200 разработчиков

Здесь в игру вступает *concurrency*. Если 15–25% команды активно работают с агентами, инфраструктуре нужно держать 30–50 hot 128K-сессий.

Ни один сервер в одиночку с этим не справится. Доступные архитектуры:

  1. Экономичный Blackwell-пул: 15–25 узлов по 8×RTX PRO 6000. Высокая сложность эксплуатации.
  2. B200-пул: 5–8 узлов по 8×B200. Правильная архитектура (TCO $\approx$ 300–900 млн ₽ за 6 лет).
  3. Гибрид: 1–2 узла B200 (heavy-задачи) + пул RTX PRO 6000 (standard-контекст) + API fallback.

Для такого масштаба 128K не должен быть дефолтом. Требуется жесткая Context Policy: репозиторий не загружается в prompt монолитом, а подается через retrieval, file ranking и symbol index. Обязательны prefix caching, sticky sessions и умный gateway-маршрутизатор. Без этого даже пул из B200 превратится в неоправданно дорогой KV-cache storage.

Почему H100 уходит в прошлое

Архитектурно H100 оказывается в слепой зоне для on-prem coding на GLM-5.1:

  • Для FP8 — не хватает памяти (80GB против 141GB у H200).
  • Для NVFP4 — нет аппаратной поддержки (нужен Blackwell).
  • По цене в РФ — не дает преимуществ ни по объему VRAM, ни по плотности вычислений.

Закупать H100 под эти задачи в 2026 году имеет смысл только при наличии экстремального дисконта.

Финальный вывод

NVFP4 действительно меняет правила игры, позволяя запускать тяжеловесный GLM-5.1 на RTX PRO 6000 Blackwell. Но он не решает проблему прожорливости длинного контекста.

Главная метрика инфраструктуры — это не цена GPU или стоимость токена. Это количество активных 128K coding-сессий, которые кластер может держать с приемлемым TTFT.

Центральный архитектурный выбор сегодня выглядит так: GLM-5.1-NVFP4 на Blackwell против GLM-5.1-FP8 на H200/B200 против внешнего API. И чтобы on-prem победил, управлять потреблением контекста придется не менее тщательно, чем управлять самими серверами.
